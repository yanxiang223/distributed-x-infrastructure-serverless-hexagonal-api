# 架构说明

## 1. 设计目标

本实践演示如何用 **六边形架构（端口—适配器）** 组织一个 Go 语言无服务器应用，
让业务规则与云服务实现彻底解耦：

- **领域层不依赖任何云服务**：商品规则、事件契约、错误语义全部位于 `domain/`，
  只通过 `types.Store` 与 `types.Bus` 两个出站端口与外部交互。
- **云服务细节集中在适配器**：数据库访问封装在 `store/`，事件投递封装在 `bus/`，
  网关协议翻译封装在 `handlers/`。更换底层实现不影响领域逻辑。
- **部署单元与入口解耦**：同一份领域代码被多个函数入口复用，
  每个入口只决定「暴露哪个能力」与「挂载哪些端口」。

## 2. 组件与职责

| 分层 | 目录 | 职责 | 依赖方向 |
|---|---|---|---|
| 领域层 | `domain/` | 商品读写规则、领域事件契约与发布时机 | 仅依赖 `types` 端口 |
| 端口 | `types/` | `Store` / `Bus` 端口定义与数据结构 | 不依赖任何实现 |
| 出站适配器 | `store/` | 兼容接口实例访问、内存实现 | 实现 `types.Store` |
| 出站适配器 | `bus/` | 事件通道投递、CloudEvents 映射与分批 | 实现 `types.Bus` |
| 入站适配器 | `handlers/` | 网关事件解析、响应封装、执行超时桥接 | 调用 `domain` |
| 入口 | `functions/` | 组装依赖并注册函数执行入口 | 组装以上各层 |

## 4. 请求链路

以 `PUT /{id}` 为例：

1. API 网关按 API 定义匹配请求，把路径参数 `id` 与请求体组装成事件下发给 `put-product` 函数。
2. `handlers.RuntimeHandler` 反序列化网关事件，并依据运行时剩余时间预算构造带截止时间的执行上下文。
3. `APIGHandler.PutHandler` 解析路径参数与请求体，做协议级校验（参数缺失、请求体为空、Base64 非法）。
4. `Products.PutProduct` 解析并校验商品对象（JSON 合法性、路径与载荷主键一致性），
   读取当前值以区分新增与更新，写入存储。
5. 写入成功后，`ProductsEvents.PublishProductChange` 通过 `types.Bus` 端口发布领域事件。
6. 处理结果按网关响应结构返回，`handlers` 统一封装状态码、响应头与响应体。

## 5. 事件链路

商品变更事件在本函数进程内同步发布，订阅方按事件类型过滤后路由：

| 事件类型 | 触发时机 | 事件载荷 |
|---|---|---|
| `ProductCreated` | 写入前该主键不存在 | 新增后的商品对象 JSON |
| `ProductUpdated` | 写入前该主键已存在 | 更新后的商品对象 JSON |
| `ProductDeleted` | 删除前该主键存在 | 被删除的商品对象 JSON |

事件采用 CloudEvents 1.0 结构投递，关键字段映射如下：

| CloudEvents 字段 | 取值来源 |
|---|---|
| `id` | 商品主键 + 随机值，保证同一事件来源内唯一 |
| `source` | 固定为 `products-api` |
| `type` | 上表中的事件类型 |
| `subject` | 商品主键 |
| `data` | 商品对象的 JSON 结构（非转义字符串） |
| `time` | 事件发布时刻（RFC3339，UTC） |

> 事件投递为**单次尝试**：投递失败不回滚已提交的写入，也不改变接口响应，
> 失败详情记录到云日志服务以便追溯与人工补偿。详见第 7 节。

## 6. 部署单元

| 函数 | 触发方式 | 挂载端口 | 说明 |
|---|---|---|---|
| `get-products` | `GET /` | `Store` | 按页返回商品列表 |
| `get-product` | `GET /{id}` | `Store` | 返回单个商品，不存在时返回 404 |
| `put-product` | `PUT /{id}` | `Store` + `Bus` | 写入并发布 `ProductCreated` / `ProductUpdated` |
| `delete-product` | `DELETE /{id}` | `Store` + `Bus` | 删除并发布 `ProductDeleted` |

四个函数共享同一份领域层与适配器代码，各自编译为独立可执行文件。
写入类函数额外注入事件通道标识并挂载 `ProductsEvents`；查询类函数不挂载，不产生任何事件。

## 7. 关键设计决策

### 7.1 存储适配器复用线协议客户端

兼容接口实例对外提供与既有线协议一致的接口，因此 `store/geminidb.go` 复用该协议的
客户端 SDK，只改动两处：

- `BaseEndpoint` 指向实例负载均衡地址；
- 凭据改为实例自带的数据库账号，而不是 IAM 访问密钥。

区域字段仅参与请求签名，不参与路由。

### 7.2 数据面鉴权使用实例账号

兼容接口的数据面**只接受实例自带的数据库账号**（固定用户名 `rwuser` + 实例管理员密码），
不接受 IAM 凭据与委托临时凭据，也不支持会话令牌。因此存储适配器使用静态凭据构造客户端。

而事件通道属于管控面开放 API，使用常规访问密钥鉴权，两者互不影响。

### 7.3 领域事件在写操作成功后同步发布

商品变更必须产生领域事件是本领域的业务不变量，因此事件发布挂在 `Products` 领域服务上：
写入成功后立即发布，发布失败只记录日志，不回滚写入、不改变接口响应。

这一取舍保证：

- 接口响应时间不受事件通道可用性影响；
- 写入与事件在同一请求生命周期内完成，链路可观测、易排查。

代价是事件投递为单次尝试，没有平台级的自动重试。若业务要求更强的事件送达保证，
可改为在写入前落一条待发布记录（发件箱模式），再由独立任务重试投递。

### 7.4 路径参数的双重解析

网关按 API 定义映射路径参数并随事件下发。为避免映射配置缺失导致接口不可用，
`handlers.pathParam` 在取不到映射值时回退到从请求路径末段解析，
保证 `/{id}` 的语义稳定。

### 7.5 执行超时预算桥接

函数运行时以 `(payload []byte, ctx RuntimeContext)` 调用入口，而领域层使用标准上下文。
`handlers.executionContext` 依据运行时给出的剩余毫秒数构造带截止时间的上下文，
并预留少量时间用于响应序列化，使领域调用能在函数被强制中断前主动收敛。
